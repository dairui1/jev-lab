Jev 接进 Codex 内置 Computer Use

在 jev-ultrafast 与 Cline jev-browser 之后一天，出现了第三种接法：不带自己的执行层，把 Jev 的决策回路塞进 Codex 已有的 mcp__cua_repl（Computer Use REPL）里，用 CUA 的 AX 树观测、CUA 的 click/setValue 执行——同时覆盖浏览器 tab 和原生 macOS 应用。这一页把它读完，并与前两者做三方对比。

三方分工写得很清楚：Codex 理解目标、准备文本、划定允许的控件、最终验证；Jev 一次请求选 operation + 兼容 target；Computer Use 观测并执行。作者明确引用了 ultrafast（多 head 策略）和 Cline（有界会话复用），0.2.0 就是把 ultrafast 的 fan-out 移植过来。

入口
SKILL.md 指导 Codex 在 cua_repl 里 await import('PLUGIN_ROOT/scripts/codex-adapter.mjs')，createCodexJev({target, client, goal, clickLabels, textSlots, verify, …}).run({maxMs:18000, maxActions:8})
执行体
Codex CUA 的 target.getAXState({disableDiffing:true}) / click(id) / setValue(id,text) / scroll(id,dir,1) / pressKey；kind:'app' 或 'tab'
Jev 接入
直连 api.typesafe.ai/v1/systemone，但经过一个本机 loopback bridge（随机 127.0.0.1 端口、一次性 Bridge token、pin 上游、拒绝 Origin 头）——因为 CUA 沙箱可能没有 proxy，也不该持有 key
文本模型
没有。TYPE_TEXT 从 Codex 预置的 textSlots[{name,value,fieldLabel}] 里选一个槽位；字面值永远留在本机
凭据
setup.py 起临时 loopback 页面让用户自己粘 key → ~/.config/codex-jev-desktop/config.json（0600）；插件代码与 Codex 对话都不接触 key
测试
123 个离线 node:test；实测样本（非受控对比）见下

回路：三个执行域，一次 Jev 请求

每个 run() 是一个 ≤18 s / ≤8 动作的 chunk（MCP 工具调用有超时），会话对象留在 REPL 里，Codex 可反复 session.run() 续跑。Jev 的 DONE 永远不被采信：verify(raw) 在每次决策前和每次动作后本地跑，Jev 说 DONE 但 verify 没过 → failed_verification。

它和前两个的核心不同

观测是 AX 文本树，不是 DOMCUA 返回类似 [12] button 预览 的缩进文本，parseAX 用一条大正则解析角色/标签/Value/ID/checked，并把 按钮/文本栏/复选框 等中文 macOS 角色映射到英文。因此天然覆盖原生 app（Calculator 实测），但没有 DOM 节点身份和遮挡检测——README 自己承认“CUA element-index freshness is not equivalent to DOM node identity”。
动作空间由 Codex 事先白名单化ultrafast/Cline 把页面上所有可见控件都交给 Jev；jev-desktop 只把匹配 clickLabels（精确串或受限正则，拒绝空匹配和“Button|删除文件|哨兵”全中的宽泛模式）的控件放进候选。会话选项在构造时冻结，后续改数组也扩不了权。超过 240 个候选直接报错让你缩范围。
没有第二个文本模型Codex 已经知道该填什么，所以 TYPE_TEXT 的 target head 是 fill_<node>_<slot>：Jev 选“哪个字段填哪个预置槽”，值本地 setValue。还多了 FILL_GROUP：多个独立字段一次决策、逐个填、每填一个重新观测。省掉 mercury/gemini 那一跳，也省掉泄露。
三层安全网① 标签正则：发送/发布/支付/删除/登录/submit/checkout… 直接不进候选，返回 needs_codex_review；Return/Enter/Delete 快捷键被禁用；② 目标名含 codex/Terminal/password/keychain 的 app 拒绝创建会话；③ 双门槛：operation 和 target 的 confidence ≥ .65 且 probability ≥ .70，否则 low_confidence 交还 Codex。
Key 隔离靠 loopback bridgeCUA 沙箱不该持有 TypeSafe key，也可能没有出网 proxy。于是在宿主 shell 起 bridge-server.mjs：随机端口、mode-0600 descriptor 里放一次性 token、只接受 POST /v1/systemone、拒绝带 Origin 的请求、请求体 ≤256 KB、上游 15 s 超时、idle 5 min 自退。CUA 侧只拿到 token。
确定性快路径绕开 Jevfast-path.mjs：已知搜索 URL 直接开 tab，用 AX 树验证结果（URL query 匹配 + 标题 xxx_百度搜索 + content_left 下有 heading），零 Jev 请求。SKILL.md 反复强调“别因为装了这个 skill 就为一个搜索开 Jev 会话”。

结论

“Jev 只做选择”走到了极致

前两者里 Jev 还要从全页控件里挑；这里 Codex 先把候选缩到白名单，Jev 只在“Codex 允许的几个控件 × 几种操作”里选。文本也不生成，只选槽位。Jev 的角色从“浏览器 agent 的大脑”退成“在主模型划定的小格子里快速做多步决定”。

正确的落点：省的是主模型往返，不是网络

README 直说动机：“Returning to the main agent after every UI click adds latency and loses short-term action context.” 一个 chunk 内 3 次 Jev 决策 + 6 次 mutation 不需要回 Codex；否则每步都要 Codex 看截图/AX 再决定。速度收益来自这里，而不是 Jev 比 Codex 快多少。

安全设计比前两者更“硬”

Cline 靠 prompt 让 Jev 返回 REVIEW；jev-desktop 靠代码：候选构建阶段就用正则把消费性控件踢出去，会话选项冻结，双门槛，DONE 不采信，poisoned 会话不可复用。代价是 Codex 要写更多前置配置（labels/slots/verify/scopeCheck）。

弱点也明显

AX 文本树正则解析脆（依赖 CUA 输出格式）；无节点身份/遮挡检测；观测慢；fast-path.mjs 是百度专用硬编码；实测都是单样本；单人项目，一天内从 0.1 到 0.2。适合读思路，不适合直接依赖。

三者一句话：ultrafast 证明“选择而非生成”能在真实网页上跑到 7 秒；Cline 把它包成沙箱化、可录像、可交还的工具；jev-desktop 则把决策回路搬进主 agent 已有的 Computer Use 里，让 Jev 在主模型划定的白名单内连做多步——覆盖原生 app，且不需要第二个文本模型。

如果要做“Claude Code / Codex + Jev”的集成，最值得抄的是 jev-desktop 的 API 形状：createSession({goal, clickLabels, textSlots, verify, scopeCheck, observations}) + chunked run({maxMs, maxActions}) + 12 种明确的交还状态。决策问题的构造（buildDecisionSpace）直接复用 ultrafast 的 fan-out 即可。
